Data contract · the what

From conversation to data contract

Maxi (category manager) needs to know which brands barely sell. John owns the sales data. Each answer becomes part of the contract.

Maxi · category managerWhich of our brands barely sell? I want to talk to them, run a campaign, or take them out of the assortment.
John · product owner, salesLet's make that a data product with a contract: slow selling brands.
+ purpose
John · product owner, salesWhat do you need to see per brand?
Maxi · category managerHow many of its products sell slowly, and when one of them last sold.
+ schema
John · product owner, salesBrand as in our product catalog?
Maxi · category managerYes, the brand everyone in the company means.
John · product owner, salesThen we link it to the Brand concept in our ontology.
+ semantics
John · product owner, salesWhen is a product slow-selling? Do returns count as sales?
Maxi · category managerNo sale in six months. And returns are not sales.
+ definition
Maxi · category managerOne row per brand, please. No duplicates.
+ data quality
Maxi · category managerI look at it every Monday morning.
John · product owner, salesWe refresh it daily.
+ SLA
Maxi · category managerWho do I ask when something looks off?
John · product owner, salesUs, the sales team.
+ owner
John · product owner, salesAnything it must not be used for?
Maxi · category managerIt is about brands, not people. Not for rating individual buyers.
+ terms of use
John · product owner, salesWe serve it from Snowflake. The contract is done, now the agent can build it.
+ server

  - name: slow_selling_brands
    physicalType: table
    properties:
      - name: brand
        logicalType: string
        required: true
        authoritativeDefinitions:
          - type: semantics
            url: ontology/brand#brand-name
      - name: slow_selling_products

        required: true

      - name: latest_sold_date
        logicalType: date
        description: When a product of the brand last sold

      - type: sql
        description: One row per brand
        query: SELECT COUNT(*) - COUNT(DISTINCT brand) FROM slow_selling_brands
        mustBe: 0

    value: 1
    unit: d

Implement a data product

Turns a data product from Entropy Data into a working dbt pipeline, and proves it works.

Tools
entropy-datadbtdbt-oldatacontract
Steps
  1. Pre-checksdbt project exists, all four CLIs are installed, entropy-data connection test succeeds.
  2. Resolve the data productentropy-data dataproducts get: name, owner, output ports.
  3. Fetch the data contractentropy-data datacontracts get, saved under models/output_ports/v1/.
  4. Translate the schema to dbtOne model per contract table, columns cast to Snowflake types, tests from the contract.
  5. Wire the input portsEach approved access becomes a dbt source, with the upstream contract as a trust snapshot.
  6. dbt parseFix obvious mistakes before anything runs.
  7. dbt-ol runMaterializes the tables in Snowflake and ships lineage to Entropy Data.
  8. dbt testnot_null, unique, and accepted_values from the contract.
  9. datacontract testChecks the live Snowflake data against every rule in the contract.
  10. Stamp as builder-managedMarks the data product in Entropy Data as built with this plugin.
  11. Final reportStatus of every artifact: created, updated, passed, failed.
The contract is the source of truth for the schema, not for the logic.

FAQ

Questions

What is a data product?

A data product is a unit of data, code, and metadata, owned by one team, that offers its data to others through output ports. Each output port is described by a data contract. Data products are defined in the Open Data Product Standard (ODPS).

What is a data contract?

A data contract is a YAML document in the Open Data Contract Standard (ODCS) that states everything guaranteed about a dataset: schema, semantics, data quality rules, SLAs, owner, terms of use, and where the data lives. The open-source Data Contract CLI tests real data against it.

How do you build a data product with AI?

Give a coding agent such as Claude Code three inputs: a data contract that says what to build, a skill library that says how to build it (pick one from the skill hub), and a data marketplace with the data to build on. Then prompt it to implement the data product. The agent requests access to input data products, generates a dbt project, runs the pipeline, tests the data against the contract, and publishes the data product with test results and lineage.

What does contract-first mean?

Contract-first means agreeing on the data contract with the business and the consumers before any data is extracted or any pipeline is written. The contract becomes the specification the coding agent implements and the test the result must pass.

Which standards and tools are used?

The Open Data Contract Standard (ODCS) and the Open Data Product Standard (ODPS) from the Linux Foundation, Apache Ossie for semantics, dbt and Snowflake for the pipeline, the Data Contract CLI and Data Product CLI for testing and publishing, and Entropy Data as the data marketplace.
